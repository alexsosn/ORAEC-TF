# Research — Installed Text-Fabric app resource (#95)

2026-10-20. ORAEC-TF source package is setuptools `src` layout with `tool.setuptools.packages.find` and no declared package-data. `MANIFEST.in` includes only `schema/core.json`. Root `app/config.yaml` (standard TF 13.1 advanced app config) is outside the Python package. The current installed-wheelhouse smoke verifies wheel imports and native TF conversion but **explicitly says** the app was not tested. Browser docs require a checkout. The resulting wheel-only user has no portable way to address the TF app.

Text-Fabric 13.1 `tf.browser.start` documents `tf app:/path/to/app --locations=/path/to/tf` for a local app. The app itself is just a config directory, no custom server, fonts, data, or network requirement. The wheel is platform independent (`py3-none-any`).

Decision: preserve root `app/config.yaml` for clone-mode browser, duplicate *only that same software configuration* under `src/oraec_tf/tf_app/config.yaml` as setuptools `package-data`, enforce strict byte equality via regression to avoid drift, and expose `oraec-tf app-path` as a single absolute filesystem path. A normal `pip install` of a wheel unpacks this resource into the site package; no special dependency/runtime hooks. Do not make a hosted browser, fetch corpus, or alter the standard Text-Fabric app. No source/TF data enter the software wheel.

Release correctness: wheelhouse offline installed smoke must invoke `oraec-tf app-path` **outside the repo**, verify its resolved path is within the venv and contains an app config identical to canonical root at build time, then use real `findAppConfig` and `tf.advanced.app.App` against a freshly generated synthetic native TF graph; `App.pretty` suffices for this packaging ticket because true HTTP route E2E on pinned full source is already separately checked in merged #93. Do not conflate existing wheelhouse `--no-deps` with independent dependency-resolving offline release #59; upstream tf-build #60 remains outstanding.
